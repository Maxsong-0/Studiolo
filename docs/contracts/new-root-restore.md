# 新根恢复：取回副本怎么核、怎么放、哪些 owner 能恢复

T-204，2026-11-15。实现了两层：备份包里的「取回副本」（只读核验，逐字节核对着放到新目录），和主服务里
按名单走的恢复编排。真实 Broker、Auth、人侧账本的用例在测试箱上通过。**没有验证的**：真实 restic 取回的
目录（用例里是把真实封存整棵复制一份来模拟）、Auth 离线恢复工具接在后面的一整轮、最终切换。
本文件不是「生产上能做新根恢复」的证明。**现在整次恢复都会被拒绝**（2026-11-16 用户拍板「先整体拒绝，另立
任务补」）：Auth 在每份生产封存里都在场，而它恢复之后必须做的撤权还没有能用于生产的入口，见下面第 2 步。

相关契约：[恢复契约](../m2/checkpoint-recovery-contract.md)「新目录恢复」、[暂存与封存](checkpoint-staging.md)、
[备份生产者](backup-producer.md)。

## 取回副本（`RestoredCheckpoint`，在 `studiolo-backup`）

从远端取回的封存目录放在哪都行，过了保留期也能核。它和上传用的 `SealedCheckpoint` 是两个类型：追加执行器
只收后者，取回的副本换不成上传能力（把副本放回同名目录再按上传来源重开，仍然被拒，有用例）。

`RestoredCheckpoint::open(目录, 引用, 截止时间)` 的条件：

- **引用（checkpoint 标识加 `seal.json` 的摘要）必须来自可信记录**：人侧账本的准入事件，或远端最终清单。
  副本自己报的摘要不算数。
- 目录属于当前账号、整棵只读（目录 0500、文件 0400）、没有 ACL。取回之后要先把权限收成这样；
  还能被写的目录直接拒绝。
- 顶层只有 `data`、`inclusion.json`、`manifest.json`、`seal.json` 四个名字；`seal.json` 的摘要等于引用，
  清单能由票据原样重建，`data` 整棵逐字节重算后等于封存时登记的视图（多一个、少一个、改一个字节都拒绝）。

和重开原封存相比只少两条：不要求目录还在原来的路径上，不要求还在保留期内。

## 放置（`RestoredCheckpoint::extract`）

把 `data/<组件>` 复制成 `新根/<名字>`，是封存内容离开取证副本的唯一出口：

- 写的每个文件都对着已核验视图里的摘要和长度，不是「磁盘上现在是什么就抄什么」；核验之后副本又被动过，
  会在写的过程中发现并失败。
- 先写进 `<名字>.restoring`，全部落盘后才原子改名。中途失败留下的 `.restoring` **不自动清**，下次直接
  拒绝（`CleanupRequired`），由人看过再删。
- 目标名字已经存在：什么都不写、也不重新核对它的内容，原样告诉调用方（`AlreadyPresent`）。
- 新目录是属主可写的（目录 0700、文件 0600），因为各库接下来要在上面继续写。
- 新根的父目录必须已经存在、属于当前账号、0700；和取回副本要在同一个账号下，不要求同一个文件系统。

## 恢复编排（`restore_into_new_root`，在主服务的 `checkpoint` 模块）

输入：一份已核验的取回副本、一个空的新根、一次性恢复身份兑换出来的恢复记录（`RecoveryGrant`）、
人确认过的前置检查（`PreRestoreChecks`）。顺序：

1. 恢复记录必须是这个 checkpoint 的、已经有写入授权；前置检查必须全部确认。
2. **按名单定能不能恢复**（只看已核验的清单，不碰磁盘）。这一版有新根恢复协议的 owner：

   | owner | 协议 | 在场时 |
   |---|---|---|
   | Broker | 专用重绑定（`rebind_new_roots`）：保留 Vault 身份和配对标识，重建物理绑定，记 lineage | 恢复 |
   | Audit（人侧账本） | 只开已有库，链尾必须正好是清单里的水位（序号和哈希） | 恢复 |
   | Auth | **没有能用于生产的撤权入口**：现成的离线恢复工具 `studiolo-auth-admin` 只认根下 `audit`、`auth`、`owner.json` 三项，也拒绝生产路径 | 整次恢复拒绝 |
   | Control、Bridge、AgentStore、Policy | **没有** | 整次恢复拒绝 |

   后四个恢复之后必须做的事（旧类型 token 和实例失效、吊销核对、同步 binding 重建）还没有协议，硬开等于
   让旧凭据和已吊销的实例复活，所以它们任何一个在场，整次恢复在写任何东西之前拒绝（`Unsupported(owner)`）。
   Broker、Auth、Audit 任何一个缺席，或者水位缺项、Broker 还有未决写入，同样拒绝（`Roster`）。
   名单成套之后，Auth 的撤权没接上也在写之前拒绝（`Unsupported(Auth)`）：恢复出来的新根能直接起服务，
   旧会话、L3 和恢复码都还有效（2026-11-16 复审确认）。所以生产上这一步总是拒绝。下面第 3～6 步留着并有
   用例，用例经测试专用的 `AuthRevocation::PlacementOnly`（生产二进制里没有这个变体）越过这道拒绝来验，
   撤权入口和启动闸门补上之后直接复用。
3. 新根里有上一次放置中途失败留下的 `<名字>.restoring`：拒绝（`CleanupRequired`），声明接手也一样，由人看过再删
   （2026-11-16，D2-F3）。新根里已经有四个固定名字中的任何一个、调用方又没有声明「接手上一次」：拒绝，不覆盖。
4. 逐字节核对着放置四个组件：`canonical`→`vault`、`writer-data`→`data`、`audit`→`audit`、`auth`→`auth`。
   名字是固定的，不由调用方给；`auth` 和 `audit` 这两个名字正是 Auth 离线恢复工具要的布局。
5. Broker 重绑定；回执里的 Vault 身份和配对标识必须等于清单里的。
6. 只开已有的人侧账本，核链尾。第一次恢复时链尾必须正好是水位那一条；接手上一次时后面可以多出恢复
   自己记的事件，但水位那一条必须原样还在。

每一步都记进恢复记录：`PreRestoreChecksCompleted`、`PhysicalRebindIntent`、`PhysicalRebindOutcome`。
第 1～3 步的任何拒绝都发生在写之前，恢复记录里也不多一行（有用例）。

成功返回**不等于服务可以上线**，还剩两步，都不在这里做：

- 在同一个新根上跑 Auth 离线恢复工具，废止旧会话、L3 和恢复码；用同一个恢复标识。做完由人把
  `AuthInvalidated` 记进恢复记录（事实判定见恢复工具包的 `AuthRestoreInvalidation::check`）。
- 最终切换（先记 Intent 再记 Outcome），以及启用双向同步之前的门禁（`BidirectionalSyncGate`）。

这里不建空库、不补默认 owner：名单里缺席的 owner，新根上不会出现它的目录。

## 已知限制

- **现在整次恢复都会被拒绝**。要补的是：能用于生产的 Auth 撤权入口（接受这个新根布局和生产路径），
  「撤权做完之前新根不能打开」的启动闸门，再把 `AuthRevocation::Missing` 那道拒绝换成真实的撤权编排。
  （放置之前的预检已经把 `<名字>.restoring` 残留算进去，2026-11-16。）
- **带黑板的部署即使补了 Auth 也恢复不了**（名单里有 Control、AgentStore、Policy）。要补的是这三个 owner 各自的新根
  恢复协议，不是编排：AgentStore 要让旧类型 token 和实例失效，策略库要先核对吊销，Control 要和 Broker
  的重绑定对上。双向同步（Bridge、Transport、Plane）同理。
- 编排是库函数，还没有命令行入口；恢复工具包（一次性恢复身份、恢复记录）的加密存取也还没有实现。
  真要演练，这两样要先补。
- 「接手上一次」的路径没有用例，也不做核对：已经在新根里的组件不重写、也不重新核对内容，靠 Broker 自己的
  lineage 判断上一次停在哪；账本链尾允许多出条目，多出的是什么不看。
- 取回这一步（restic restore 到一个目录、收权限）是人按运行手册做的，没有代码，也没有拿真实 restic 验过。
- 各 owner 的水位只核到这里列的程度：Broker 核身份和配对标识（不核已提交序号），Audit 核链尾，Auth 不核
  （留给它自己的工具）。字节层面的完整性由取回副本的整棵重算保证。
