# 最终记录与原作业恢复

最终成功需要两份远端快照：数据快照，以及引用它的最终记录。`BackupWorker::run` 只接收真实 `SealedCheckpoint`，不再接受调用方另造的票据／manifest。作业上传前持久原 `SealedReference`；数据核验和最终提交都绑定原 `JobKey`，不以 latest 或重分配序号重试未知结果。

`FinalManifestDraft` 固定绑定原键、seal SHA、原 manifest 及其 SHA、数据快照完整 ID、原路径／期限和数据核验时间。私有字段、严格反序列化、规范 JSON 与 64 KiB 上限使预期字节跨重启保持不变；其中没有正文或凭据值。这个 DTO 自身不是远端 IO 证明。

## 先持久，再写远端

1. 实际上传退出后，原生 `RemoteProbe` 证明原作业唯一快照、完整目录树与每个文件的 SHA／长度。
2. 在同一次状态替换中保存 `CommittingFinalManifest` 与确定 draft。保存失败不得开始最终远端写入。
3. 原生 `AppendRunner` 只能消费自己刚才核验得到的同一 draft。调用方自造或改过的 DTO 不会获得上传权限。
4. 先查原最终 tag，已有唯一且字节相同的记录就读回。缺失才执行本次唯一的 `backup --stdin --stdin-filename /studiolo-final-<原JobTag>.json --tag <原JobTag>.final`；不接收宿主机文件路径或 stdin-from-command。输入最多 64 KiB，和 stdout／stderr 一起非阻塞推进，完成立即关闭 stdin。原源时钟与进程组回收仍生效。
5. 必须查询唯一完整最终快照、核它的全部节点只有一个固定普通文件，并流式读回完整长度和 SHA，再重查唯一快照。退出 0 或本地 manifest 文件都不能代替这些事实。
6. 先持久完整 `FinalManifestReceipt` 与 `AuditPending`，再缓存本地 manifest 和追加成功 Outcome。AuditRecord 的完整性、事件键／phase／action／payload 都必须匹配原事件。
7. 成功 Outcome 已确认后，作业 Succeeded、最后最终回执、三个时间戳和恢复点指针在同一次原子状态保存中提交；不能先写成功再单独写指针。

本地缓存写失败保留远端真实回执，仍待本地补记；不能改称远端上传失败。成功 Outcome 带数据／最终快照 ID 和稳定时间，幂等补记不重造载荷，且明确不包含在本次 checkpoint 截止前的 Audit 快照内。

## 崩溃、断线与过期

上传或核验错误留下对应未知阶段。重启把执行中阶段转未知；上传恢复只读原快照，不重传数据。最终提交错误可能已经写到远端，必须保留原 draft 和 FinalManifestAck 未知。即便崩溃发生在 draft 保存与远端调用之间，也不猜测未写入而盲目再次提交。

独立 `FinalManifestProbe` 只持固定 Runtime，没有 Source；它只读取由原键导出的非正文最终记录。原本地封存到期或路径消失后，仍可用持久 draft 核对最终 ACK，不能借机续期正文读取。每次独立查询最多五分钟，仍要求固定包、受保护凭据、原临时目录、真实 UTC／单调时钟和进程回收。

查询错误、多个候选或内容不一致继续未知。成功完整查询仍缺失时，原源到期前保持未知，到期后才能记录最终提交失败；这不宣称数据快照从未上传。已经固定了远端回执的 AuditPending 仅补记原事件，无需重新上传或重新生成时间戳。失败／未验证的 Outcome 也在状态里固定，审计不可用时保留 pending_failure，补记前禁止另一作业开始。

## 持久边界

状态 schema 2 拒绝旧版本；此前未上线的 Rust 原型状态不能自动升级成真实远端已提交。当前生产 Python 备份不使用此目录，不受这次 schema 变更影响。

最多 128 条作业记录、32 个排队项、一个活动作业。排队前只回收旧终态，保留最后成功作业及尚未审计的失败；序号严格递增，不复用。读取时检查重复序号、阶段／时间戳形状、原封存、pending draft／receipt、最后成功记录与指针的配对。状态 1 MiB、本地 manifest 缓存 4 MiB，序列化过程中即拒绝越界。首次 seed 只能依据同一成功作业的远端回执及匹配缓存标记。
