# Broker 封存与新根恢复

T-204，2026-11-13。本文描述实际 Broker 存储机制；完整七方协调器、真实 Audit
回调、inclusion plan、独立 Worker 和启动装配仍须在组合根接齐，不能据此宣称
灾难备份或生产恢复验收已完成。

`FsVaultBroker::freeze_checkpoint` 移入原实例，保留原 canonical 写租约。冻结句柄
不导出普通读写接口；`thaw` 在任意失败之后都返还原实例，既不重开第二写者，也不
回滚或清理活动根。Prepared 可读仍视为未排空；永久写者状态和正文 outbox 必须空闲。

核对由两端完成：Broker 从固定存储重建原事件；可信组合根用 FrozenAudit 核对
完整事件、原 offset 和 hash。Broker 不依赖 Audit crate，也不允许公开 DTO 顶替
自己的永久记录。核对覆盖正文永久双 ACK、文件操作请求/终态/双 ACK，以及最后
保留的维护槽。还从幂等终态反查母本，整个请求目录被删掉也不能冒充无审计历史。

核对时先定格 canonical 和 writer-data 两棵树（BUG-045，2026-11-22，`checkpoint/capture.rs`）：逐层列目录、
逐个打开文件留着句柄、记下 dev/ino/长度/权限/属主/修改时间，不读内容；核完重放和回执再逐个复核两棵树和定格时
一样，核过的就是定格那一刻。定格不引用写者实例：`take_capture` 交出 `BrokerCapture` 之后写者可以解冻、照常改，
写者只用新建再改名换上、从不原地改文件，句柄指着的旧 inode 内容不变。不建硬链接：写者到处要求链接数为 1，
硬链接会让解冻后的正常读写报错，中途被杀还会让写者起不来。能同时开着的文件数是本进程打开文件数软上限的一半
（人侧配了备份生产者时启动先调 `raise_open_file_limit` 把软上限抬到硬上限；抬法和额度都在写者的
`checkpoint/open_files.rs`、`capture.rs`，local-server 不碰 rlimit，那里只有 `studiolo-process-safety` 的收紧），
不够就定格失败（`WriterLimitExceeded`），不半拍。
摘要覆盖文件名、目录结构、空目录、文件长度与全部正文，在导出时从句柄边拷边算（和以前的整树扫描同一套写法）。
256 KiB 流式缓冲、两根合计 100 万节点/512 GiB、64 级深度和截止时刻限制全部适用。拒绝链接、特殊节点、跨设备、
非本用户节点和源身份漂移。

两个目标必须预先批准、0700、为空，且与源（定格时记下的两个源根路径和身份）及彼此在路径和物理祖先上均不重叠。
动目标之前逐个句柄 fstat 一遍，有文件被原地改过就整份失败、目标不动（`CaptureChanged`，人侧日志写
「导出：owner Broker 定格之后被改过」，账本照旧记 `barrier_not_established`）；拷贝时每个文件拷前
拷后再核一次。这个核对只看元数据、不比内容（比内容就得在窗口里读全部正文），抓不到两种原地改写：同一个时间
戳节拍里（ext4 约 4 毫秒）改成同样长度；改完用 `utimensat` 把修改时间设回去。写者自己从不原地改，这两种只能
是别的同用户进程改写者的文件。ctime 和链接数故意不比：解冻之后写者删掉或换掉原文件、给文件改名都会改它们，
内容不变，比了会误报；ctime 的粒度和修改时间一样，加上也补不了同一节拍的那种。只创建 0600 独立文件和 0700 目录；文件与父目录同步后再扫描一遍目标，摘要必须等于拷贝时算的那一个。
没有硬链接、覆盖现有目标或递归清理。失败残片不能作为恢复点。
本机制的全量物化不能替代组合根先行完成的逐对象 inclusion plan 和最终原子封存。

封存保留原绑定字节。新目录恢复必须由 Broker `rebind_new_roots` 完成：保留 Vault
UUID/pair_id，重绑两个主根、已启用 history/meta-v1、maintenance-v1 和文件操作
目录/删除隔离区。空历史只在写者水位未前进、无操作/终态且目录确实为空时记录为
未启用。缺失已启用存储、半初始化或逻辑配对不符均拒绝。

原审计事件、幂等键、墓碑内容摘要和历史内容证明不改写。删除对象可以在新根上
重新核验历史字节并执行真正的墓碑恢复。lineage 尚为 Rebinding 时，普通打开和
初始化都拒绝，即使两个主 binding 已写完；只有显式恢复接手可继续。

T-212（2026-11-16）：lineage 第 2 版多记一个恢复标识 `restore_id`（1～55 个字母、数字或 `-`，和 Auth
撤权记录同一套规则，`valid_restore_id`），`NewRootRebind` 跟着加，格式不对在写任何东西之前拒绝。接手上一次
中途失败的重绑定时，恢复标识必须和 lineage 里记的相同，否则 `RestoreIdMismatch`。第 1 版 lineage 照旧能读
（`restore_id` 为空），版本和字段对不上的拒绝。`read_restore_lineage(写者数据根)` 只读，主服务启动闸门和
最终切换都按它认「这是哪一次恢复」，见[新根恢复](new-root-restore.md)。108 `20261116-132450-185c`：Broker
库内用例和示例编译通过。

同日 Codex 第二意见之后：lineage 第 3 版再记 `earlier_restores`，这份数据以前用过的全部恢复标识，按先后。被封存
的根本身是恢复出来的，封存会把它的 lineage 连同 data 整棵带走：新的重绑定把它那一串加上它自己已完成的那个
标识记下来（`parent_lineage` 是它自己的标识，由主服务的编排从数据里定，不由命令行给）。这次的恢复标识是其中
任何一个，都在写任何东西之前拒绝（`RestoreIdReused`）：Auth 里留着那次的撤权记录，再用一次，启动闸门会把旧
记录当成这次的。接手停在重绑定中途的同一次恢复，沿用第一次算好的那一串。读的时候：第 1 版没有恢复标识、没有
那一串；第 2 版有合法的标识、没有那一串；第 3 版有合法的标识，那一串最多 256 个、互不相同、都合法、不含这次的；
对不上的按未知版本拒绝。有用例：从恢复出来的根的封存再恢复两代，每一代都记全之前的标识，用过的一律拒绝、
lineage 文件一个字节不变。

定向验证：108 `20261113-134846-a727` 的初始封存 5、审计回归 6、严格 Clippy、
架构 60 通过。补齐反向母本核对和恢复布局后，108 `20261113-135334-12af` 封存 7、
恢复回归 24、审计回归 6、严格 Clippy 和架构 60 全通过。最终全量/生产演练仍与
上述机制证据分开。

## 实际工作台与 Audit 接线

`CanonicalWorkbench::freeze_checkpoint` 移走正在服务的 Broker；任何失败或上层展开均返还同一个 owner。普通写者槽在窗口内为空，原唯一租约仍被持有，既不重开写者也不释放给第二进程。

`FrozenWorkbench::verify_audit` 复用线上正文、类型化文件操作和维护三个事件映射，按永久 ACK 的原 offset 读取真实 FrozenAudit，再核对完整事件和原记录哈希。相同 event_id 但 action/payload 不符，或只持有真实 offset 而哈希不符，都拒绝导出。没有新增第二套 payload 编码。

108 `20261113-141921-acd6`：3 项真实工作台接线契约、严格 Clippy、架构 62 通过。真实正文、取消文件删除及维护操作共 6 个原事件全部核对；另覆盖错误完整事件/哈希不能导出，以及超时/展开返还原实例。七 owner 全局屏障仍由最终组合根接线，不能用这个单 owner 窗口冒充全系统冻结。
