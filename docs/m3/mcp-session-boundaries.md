# MCP 会话、凭据轮换和资源边界

T-046，2026-09-12。本文描述当前实现；本地契约与部署验收分别记录在
[整体收尾台账](../m2/m2-m3-closeout.md)，不代表线上已经更新。

## 身份连续性

每个 MCP 会话同时绑定首次握手的类型和凭据摘要。POST、GET/SSE、
Last-Event-ID 续读及 DELETE 都必须使用同一凭据；只知道会话 ID 不获得读取权。
类型撤销或凭据轮换后，旧会话和旧流失效，客户端必须重新 initialize。
每次供给仍核对原有 instance 身份和路径白名单。

流交付前重新核对身份与期限；后台每秒检查过期及已撤权的会话。
断开连接、取消 HTTP future 或删除会话，不等于后台供给作业已经结束。
只有实际创建结束且传输 worker 退出后才能回收对应容量；供给作业另持工作许可。

## 会话不可用时的状态码

T-179，2026-10-15（vault BUG-029）。按 MCP 2025-11-25 Streamable HTTP「会话管理」第 2～4 条：

| 情形 | 状态码 | 客户端该做的 |
| --- | --- | --- |
| 无、错、已吊销的类型令牌（先于一切会话判断） | 401，带 `WWW-Authenticate: Bearer realm="studiolo-agent"` | 换令牌 |
| 会话号查不到、已过期、已关闭，或属于别的类型、别的凭据 | 404，不带 `WWW-Authenticate`；对外与会话不存在相同 | 不带会话号重新 initialize |
| GET、DELETE 不带会话号；POST 不带会话号且首包不是 initialize | 400 | 先 initialize |
| 请求已交给 SDK 之后凭据被吊销或轮换 | 401，带 `WWW-Authenticate` | 换令牌 |
| 请求已交给 SDK 之后会话才过期或被关闭 | 503 | 本次结果未知、不自动重放；下一次请求得到 404 后再重新 initialize |
| 身份库读不出来（认证、查会话或交给 SDK 之后的复核时） | 503，不带 `WWW-Authenticate`；会话保留 | 稍后用原会话重试；不换令牌、不重新 initialize |
| 进程收到 SIGTERM／SIGINT 之后到达的新 initialize、新请求、新 GET 流（见「停服」） | 503；DELETE 照常 | 稍后重试；进程重启后原会话已不存在，得到 404 再重新 initialize |

401 只表示凭据本身失效。会话过期不能回 401：Claude Code 收到 401 一律当成令牌过期、转去 OAuth
重新认证，而 Studiolo 没有 OAuth 端点，入口前的 Cloudflare Access 也会拒绝它的动态客户端注册，
结果只能新开会话。Claude Code 2.1.295 收到 404 会重新握手，并把这次工具调用重试一次。

有会话的请求，rmcp 先把消息交给会话 worker、再立刻返回 SSE 响应头，所以门禁在响应头之后的那次复核
发生时请求可能已在执行。这时回 404，客户端会当成「没处理过」而自动重放，写操作可能重复，所以回 503。
响应流开始之后会话才失效的，流直接结束。两处例外：initialize 交出之后会话没能建立（含途中凭据被吊销）
一律回 503；DELETE 本身就在关闭会话，成功响应原样放行、不做这次复核。

T-180，2026-10-15（vault BUG-030）：身份库读不出来（SQLite 忙超时、I/O 错、私有存储复核失败）时，凭据和会话是否仍有效都未知，
既不能当成凭据失效回 401，也不能当成会话失效回 404 或丢掉会话。认证门、门禁查会话、交出之后的复核一律回 503、不带 challenge，
审计记 `identity_unavailable`；响应流暂停交付、不结束，后台每秒的清理也不丢这类会话，身份库恢复后同一会话接着用。
POST 响应体 30 秒的期限照旧：停顿超过期限时按原规则结束响应、回收会话，客户端下一次请求得到 404 后自动重新 initialize，
不会转去重新认证。工具内部的复核读不出来，返回「身份库不可用」错误，而不是「会话无效，请重新握手」。

HTTP 文本供给（`/read/*`，自定义 `Studiolo-Session-Id`）不归本节管，仍按 [HTTP 文本供给](http-text.md) 回 401；身份库读不出来时两边一样回 503。

## 固定预算

| 对象 | 上限 |
| --- | --- |
| 全部会话（含预占与待清理） | 128 |
| 每个类型的会话 | 32 |
| 每分钟新建尝试 | 32；失败、取消不退还次数 |
| 同时活动传输 | 16 |
| 同时执行的实际供给 | 16 |
| initialize / 请求响应头等待 | 30 秒 |
| 空闲期限 | 15 分钟；成功供给才推进活动时间 |
| 绝对期限 | 1 小时 |

容量耗尽返回 429，带 Retry-After；存储或传输不能确认时拒绝继续。
这些边界不改变 agent 读取审计降级规则，也不向 agent 提供内容写入权。

## 断线与重试

仍在进行的流可在原会话、原凭据下重连。已经完成或取消的 POST 不保存历史事件
供后续重放；它们的旧 Last-Event-ID 返回空 SSE，不表示重新读取成功。
客户端需要再次执行只读工具以获得新结果与对应的新读取审计。

SDK 正常最终响应会立即删除通道。取消或资源注销的完成通道采用零保留时间，
在下一次事件循环处理前移除。契约分别连续验证正常完成和取消后的旧事件不可回放。
这不是持久消息队列，也不承诺断电后恢复 MCP 会话。

## 停服

T-184，2026-10-15（vault BUG-033）。axum 的优雅关停要等每条连接自己结束，客户端开着的 GET 独立 SSE 流
（rmcp 每 15 秒发一次保活）却不会自己结束；旧版因此收到 SIGTERM 后一直等，直到 systemd 20 秒时强杀。现在收到信号后：

1. 门禁先置「关停中」：新会话、已有会话的新请求、新 GET 流一律 503，审计记 `server_stopping`；DELETE 照常。
2. 已进门的 POST 一直登记到它的响应体结束；全部结束（最多 10 秒，到点强制）后关闭全部会话，名下的 SSE 流随之正常结束。
3. 连接都收尾后 `serve` 返回；从信号起 15 秒仍没收尾就以退出码 1 退出。整套上限见[接入方供给契约](../contracts/agent-supply.md) §9。
