# canonical写入的下一步设计输入

2026-09-05，T-028已查重认领；旧实现已用真实磁盘复现：同进程及重开后两条
错误CAS重放测试失败，Memory对照通过。现在分域实施单写者与未决幂等，
再进入新鲜度、HTTP保存及历史界面；尚未宣称修复验收完成。

## 已复现的旧实现边界

`FsVaultBroker::mutate`先记录`receipt=None`，后验证首次CAS；重放未决记录时，
若当前revision等于目标内容revision，就补成功回执。静态可达顺序为：

1. 页面为A；请求K以错误前置B要求写C，CAS拒绝但留下未决记录。
2. 另一请求合法把A写成C。
3. 重放K可能被补成成功，回执甚至声称previous=B。

原有测试覆盖错误CAS、成功保存和成功回执重开，没有覆盖三步组合。
新增mutation_rejection_contract实跑三步：FS确实误补成功，Memory仍拒绝。
M0已通过原有测试的事实保持，但不能由此推导HTTP编辑所需的完整幂等保证。

## 独立实现边界

- 在Broker内统一跨进程唯一写者、已有根打开、Vault/数据目录绑定与根/marker复核。
  锁必须覆盖同一canonical选不同data_root，不能只锁任意数据目录。
- 比较身份文件持久锁、额外锁文件、独立守护写者三案，先确定锁生命周期和迁移兼容。
  不将仅进程内Mutex宣称跨进程单写者，不破坏已有只读预览能力。
- 定义明确拒绝、未决与完成；补成功必须有本次安装的可靠证据，不能看碰巧相同的内容。
  无法确认时保持未决并阻止新写越过；仅把CAS提前一次不解决提交后崩溃与外部同内容。
- 复用真实Revision、Precondition、原子临时安装、内容寻址旧版本和已完成回执；不开放
  原始Mutation反序列化HTTP。检查现有读/历史/幂等记录的无界读取并收敛预算。
- 新测试先覆盖失败CAS三步重放、不同data_root争抢同一Vault、崩溃阶段的未决行为、
  历史旧字节，以及根/marker替换；明确夹具注入与真实断电验证的区别。

## 后续依赖

单写者提供持久提交水位，再建立canonical完整扫描与派生索引应用水位。
扫描失败、watcher溢出、根变化、未决写入保持stale；完整重扫追平后才能恢复编辑。
M1 generation、只读namespace revision与canonical编辑revision保持区别。

保存最终须同时通过授权、可编辑路径、新鲜度和目标实时CAS；409保留双方。
已完成幂等回执只描述历史提交，不冒充当前页面。写入合法Markdown/YAML须显式验证，
不能把读取侧容错当写入许可。按最新ADR区分正文、规则/skills/能力集与生成/不可变区。

bridge后来接同一写者队列，带base revision和外部Obsidian归属，镜像仍独立。
认证摄入、白名单、冲突副本、删除熔断和双向搬运不并入首个单写者单元；
编辑的新鲜度门槛不能同时阻断bridge追赶，否则无法解除陈旧。
