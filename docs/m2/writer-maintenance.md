# 本机事务维护

`studiolo-maintain` 只处理 M2 写者的一项未决事务及其固定审计，不执行全库恢复、控制冻结解除、同步删除熔断解除或应用身份恢复。运行者使用真实本机 OS 权限；配置中的 owner 不是操作者认证，控制终端也不提供 Access、L2 或 L3 身份。

命令要求当前 real/effective UID 与 GID 分别相同；标准输入、标准错误与 `/dev/tty` 必须属于同一会话和同一前台进程组，标准输入与标准错误还必须属于同一实际终端设备。`/dev/tty` 是控制终端别名，不能用其设备号与实际 PTY 设备号比较。命令固定初始会话、进程组与实际终端设备，随后持续复验。不接受管道授权、`--yes`、正文、请求密钥、种子或身份覆盖参数，不读取任何秘密环境值或 Auth 数据库。

配置与全部根必须已存在且通过私有权限、身份与分离审批。维护使用与后台服务相同的 Broker 独占 owner 租约。后台服务仍持锁时命令会拒绝，不自动停服、初始化、迁移、修权限或创建数据库。操作者应通过已批准的服务维护流程安排独占窗口，再运行命令。

## 命令与审阅

以下命令共用四个明确的非秘密根参数：

```text
--config /私有配置目录/owner.json --vault /canonical --assets /assets --writer-data /私有写者数据目录
```

| 命令 | 额外参数 | 含义 |
| --- | --- | --- |
| `inspect` | 无 | 读取至多 64 项逻辑审阅元数据和单槽维护状态 |
| `cancel-prepared` | `--request <review_id>` | 明确取消尚未进入安装的原请求 |
| `preserve-installing` | `--request <review_id>` | 保留当前 canonical，封存 proposed/current/previous，原安装永久标记未知 |
| `cancel-restore-intent` | `--request <review_id>` | 丢失原浏览器请求键后，取消仍未开始安装的固定恢复 Intent |
| `cancel-maintenance` | `--maintenance <maintenance_id>` | 取消尚未开始执行的维护自身，原事务不变 |
| `audit-flush` | 无 | 只补记既定原请求与维护 Intent/Outcome 及 ACK |

`review_id` 与 `maintenance_id` 都是 inspect 返回的 64 位小写十六进制指纹。不要把路径、序号或正文摘要当作指纹替代。`inspect` 不要求手工确认，但同样检查真实控制终端。审计库不可用时仅输出 `audit_available:false` 和已核验状态，不报告维护成功，也不自动创建库。

固定维护槽与原目标的新审阅分别呈现。`inspect` 只有完整审阅成功才返回 `targets_status:ready` 和目标数组；目标变成符号链接等不安全对象时，若固定槽和写者状态仍可验证，则返回 `targets_status:unavailable`、`targets:null` 和诊断，不用空数组冒充“没有原未决”。固定槽或根自身失效仍拒绝。

`cancel-maintenance`、`audit-flush` 与所有操作后的状态报告只读取固定槽及写者元数据，不重新读取原 canonical/stage。报告以 `targets_status:not_observed`、`targets:null` 明示未做新目标观察；因此原目标不可读不会阻止取消维护自身或补记审计，也不会让已完成决定因报告阶段重新读目标而误报未知。三种原事务决定仍要求完整新审阅成功。

其余命令在同一控制终端显示 JSON 转义的固定审阅元数据，再要求 120 秒内完整输入动作和指纹。`audit-flush` 的确认文本为动作本身。确认最多 128 字节；EOF、额外行、非 ASCII、错误输入、终端身份变化或超时均拒绝。stdout 重定向不会隐藏确认所需的审阅信息。

终端读写不改变终端属性，使用独立非阻塞描述符和最多 25 毫秒小轮询。完整审阅 JSON 上限为 512 KiB，分段输出须在 120 秒内全部完成；短写或暂不可写时保留进度，身份变化、截止时间到或其他错误立即拒绝，不在审阅只输出一部分时进入确认。这样避开 macOS `poll` 对 `/dev/tty` 的限制；Linux 与 macOS 共用固定截止时间。生产入口没有缩短期限或跳过身份检查的测试开关。

## 审计与崩溃后收口

原 Human/Obsidian 主体、请求种类和请求键绑定保持不变。本机操作另记固定 `writer.maintenance` 事件，包含实际 UID/GID、决定、目标指纹与来源。维护 Intent 可靠持久化并取得匹配的权威审计 ACK 后才能执行；维护 Outcome 未确认前不宣告完成，也不准入新写入。

维护结果与原写入结果分开表达：`Applied` 表示本次协调执行完成，另以 `resolution` 明确取消或未知；`Cancelled` 表示维护自身已取消；`NotApplied` 表示原目标改变，本次决定未执行。任何情况都不能凭当前字节与拟写字节的哈希相同补记原请求成功。

若进程在 Intent 持久化之后、实际协调之前退出，可重新审阅后重试同一决定，或使用 `cancel-maintenance`。后者先确认固定 Intent 审计，且只允许尚未执行的同一维护票据；原目标后来漂移不妨碍取消维护自身。已经开始执行或结果未知的维护不可通过此命令抹去。

`audit-flush` 不会开始尚未执行的决定，只重送固定事件和 ACK。它先补原请求事件，再确认维护事件；同一原请求每轮只返回一个阶段，因此最多读取两轮、每轮 64 条，空批提前结束，总计至多 128 条原事件，不无限循环。输出仍有 pending 或剩余审计数量时，应再次 inspect 核验，不能把命令返回解释为全部写入已解锁。

重开 Broker 可以完成此前已经持久化决定的收尾，因此 inspect 不是零 IO 承诺。遇到审计失败、输出失败或未知结果，应保留既有存储与证据，重新 inspect；禁止自动重试协调、清库或依据文件哈希制造成功。未开始的维护可显式取消；已执行但未知的状态仍须保留证据并按既有故障处理流程调查。

维护全过程在关键步骤前后重验配置字节、五根身份/分离和 Broker 句柄绑定。不从 seed_ref 或环境值推断秘密来源文件，也不声称验证了任意环境来源。实际生产秘密来源仍由部署装配单独批准。

## 验证边界

契约使用真实临时文件系统和已有 SQLite/Broker 存储，覆盖缺库不初始化、真实 owner 互斥、配置与根漂移、失键恢复取消、原主体保留、审计失败与重开、维护自身取消、失败原子性。系统 `/usr/bin/script` 提供真实 PTY 子进程负测；缺失时测试明确失败。

短期限仅存在于 cfg(test) 私有接缝，复用生产确认循环验证真实 PTY 超时、错误确认与标准输入对象漂移。普通测试环境不实际提权改变 UID/GID；对应身份相等性由纯契约覆盖，不能当作特权环境或生产运维验收。
